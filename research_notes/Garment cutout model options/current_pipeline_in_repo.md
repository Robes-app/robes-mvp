Scope: read-only codebase research on branch `beta` at commit `facc382` (PR #243 merged on top of PR #242), 2026-11-21. ## 1. Where does a photo get read into pieces (Gemini calls, boxes, prompts, versions)?

### Takeaway
Both apps read a photo with ONE Gemini vision call that returns every piece with a fractional box `{x, y, w, h}` (not `box_2d`); the platform's is the `wardrobe_pieces` job using prompt module `wardrobe-pieces` v3 on `gemini-3.8-flash`, the legacy one is `POST /api/wardrobe/pieces` on `gemini-2.5-flash`. There is also a single-piece read with no box (`wardrobe-analyse` v5 / `POST /api/wardrobe/analyse`). Prompt versions on the platform are numbered files (`vN.ts`) that extend the previous one, switched by one line in `packages/ai/package.json`.

### Cited Findings

**Platform (the rebuild)**
- The multi-piece read is the job handler `createWardrobePiecesHandler`; it loads the photo's `master.jpg`, the closet list, and calls `deps.ai.generateJson({ feature: FEATURE, capability: 'vision.analyse', system: SYSTEM, user: buildUser(closet), images: [{ mimeType: 'image/jpeg', data: image }], schema: Output, maxOutputTokens: 4200, temperature: 0 })` — `platform/packages/jobs/src/handlers/wardrobe-pieces.ts:36-74`. Job budget 90 s (`:41`).
- The single-piece read is `createWardrobeAnalyseHandler`: same capability, `maxOutputTokens: 2400`, `temperature: 0`, no box — `platform/packages/jobs/src/handlers/wardrobe-analyse.ts:26-73`.
- Model: capability `vision.analyse` maps to `gemini-3.8-flash` (family `gemini-flash`, $0.75 in / $3.75 out per 1M tokens), with the comment "Reading a photo: the full Flash, not Lite. Lite at medium resolution missed the brand on a collar label, the print and the material" — `platform/packages/ai/src/models.ts:49-57`. Call sites never name a model id (`models.ts:1-3`).
- Thinking / resolution: for `vision.analyse` the provider sets `thinkingConfig: { thinkingLevel: ThinkingLevel.LOW }` and `mediaResolution: MEDIA_RESOLUTION_HIGH`; comment: "LOW, not MINIMAL: gemini-3.8-flash has 400d MINIMAL since 5 Nov 2026" — `platform/packages/ai/src/gemini.ts:66-82`. Response is JSON via `responseJsonSchema` built from the zod schema with `maxItems` stripped (`gemini.ts:16-29, 62-63`); output is validated by zod (`gemini.ts:105-107`).
- Multi-piece prompt text (v1 text, still used through v2/v3): "Find EVERY distinct clothing piece in this photo — each garment, each pair of shoes, each bag, each accessory — whether worn together on one person, laid flat, or hung side by side. One entry per physical piece, and each physical piece EXACTLY ONCE … Ignore the person, the room and anything that is not a piece she could file in a wardrobe. At most ${PHOTO_PIECES_MAX} pieces, the most prominent first." and the box rule: `"box": where THIS piece sits in the photo, as fractions of the image's width and height — "x" and "y" the top-left corner, "w" and "h" the size, all between 0 and 1. Tight around the piece, not the whole figure.` — `platform/packages/ai/src/prompts/wardrobe-pieces/v1.ts:66-77` (same text in `v2.ts`).
- Box schema: `Box = z.object({ x, y, w, h })` (numbers); each piece = the single read's fields plus `box`, `wardrobe_index` (int), `match_confidence` (number); output `{ no_item_detected, pieces[] (max 20) }` — `platform/packages/ai/src/prompts/wardrobe-pieces/v3.ts:24-36`. `PHOTO_PIECES_MAX = 8` — `platform/packages/core/src/photo-pieces/index.ts:12`.
- System line (pieces v3): the analyse v5 system with "file the piece in it" replaced by "file every piece in it" — `wardrobe-pieces/v3.ts:38`; analyse v5 system: "You are the fashion reader for Robes, a luxury wardrobe app. You look at one photo and file the piece in it. You never invent details: every field is read from the photo, and the one call beyond what is printed, a brand known by its signature design, is flagged for her to check." — `platform/packages/ai/src/prompts/wardrobe-analyse/v5.ts:19`.
- Post-processing of the model's pieces (`foldPieces`): dedupe by label+category, `normaliseBox` (clamp to frame; a box under 2% on a side becomes the whole frame), wardrobe match read against the numbered closet, `collapsePairs` (two Shoes entries of the same kind become one with the union box), cap at 8 — `wardrobe-pieces/v2.ts` (`foldPieces`), `platform/packages/core/src/photo-pieces/index.ts:21-31, 85-107`.
- No hit for `box_2d`, `bbox` or `bounding` (as a model field) anywhere in `server.js` or `platform/` source; the only box shape is `{x, y, w, h}` fractions (grep over both trees).

**How platform prompt versions are managed ("a new prompt version as usual")**
- Each prompt is a folder of numbered modules with a test beside each: `wardrobe-analyse/v1..v5.ts` (+ `.test.ts`), `wardrobe-pieces/v1..v3.ts`, `style-piece/v1..v11.ts`, `avatar/v1..v7.ts` — directory listing of `platform/packages/ai/src/prompts/`.
- A new version re-exports the previous one and overrides what changed: e.g. `export * from './v4'; export const VERSION = 5; export const Output = OutputV4.extend({ brand_check: z.boolean() });` and `buildUser()` built by string-replacing a rule in v4's text — `wardrobe-analyse/v5.ts:13-28`. v3 added the colour model, v4 the material, v2 the "label never carries the brand" rule (`wardrobe-analyse/v2.ts`, `v3.ts:18-21`, `v4.ts:12-17`).
- The current version is selected by the package export map: `"./prompts/wardrobe-analyse": "./src/prompts/wardrobe-analyse/v5.ts"`, `"./prompts/wardrobe-pieces": "./src/prompts/wardrobe-pieces/v3.ts"`, `"./prompts/style-piece": "./src/prompts/style-piece/v11.ts"`, `"./prompts/avatar": "./src/prompts/avatar/v7.ts"` — `platform/packages/ai/package.json:7-17`. Handlers import the unversioned path (`wardrobe-pieces.ts:9`, `wardrobe-analyse.ts:2`).
- The version is stamped on each read: `itemDna.prompt_version: VERSION` (number) for the single read (`wardrobe-analyse/v5.ts:40`) and ``prompt_version: `${FEATURE}@${version}` `` (e.g. `wardrobe.pieces@3`) for the multi read (`wardrobe-pieces/v2.ts`, `foldPieces`).
- `wardrobe-pieces` reuses the single read's field rules ("one text, so the two reads never drift") by slicing `buildAnalyseUser()` from `"label":` — `wardrobe-pieces/v3.ts:40-43`. So a new field in `wardrobe-analyse` vN+1 needs a `wardrobe-pieces` vN+1 that imports it (that is what pieces v2 and v3 are: `v2.ts` header "the field rules of wardrobe-analyse v4", `v3.ts:18-20` "the field rules of wardrobe-analyse v5").
- PR #242 shows the shape of a version bump in one PR: new `vN.ts` + `vN.test.ts`, the `package.json` export line changed, handler tests updated for the recorded version (`promptVersion: 10 → 11`), and `platform/docs/data-inventory.md` updated — PR #242 changed-files list.
- Docs say evals are required before a prompt or model change: "Evals: `packages/ai/evals/` golden inputs per feature; `pnpm eval <feature>` … required before changing a prompt version or model mapping" — `platform/docs/infrastructure.md:132`; `platform/CLAUDE.md` "prompts are versioned modules with evals".

**Legacy app**
- `POST /api/wardrobe/pieces` (rate limit 20/min) — `server.js:3611`; model `gemini-2.5-flash`; config `{ responseMimeType: 'application/json', responseSchema: PIECES_SCHEMA, maxOutputTokens: 5000, temperature: 0, thinkingConfig: { thinkingBudget: 0 } }` — `server.js:≈3624-3640`. Prompt opens "You are a fashion intelligence engine for a luxury wardrobe app. Find EVERY distinct clothing piece in this photo …" and carries the same `"box"` rule as the platform (`server.js:≈3630-3637`).
- `PIECE_BOX_SCHEMA` = `{x, y, w, h}` numbers; `PIECES_SCHEMA` = the analyse properties plus `box`, `wardrobe_index`, `match_confidence`; `PIECES_MAX = 8`; server-side `collapsePairs` — `server.js:≈3560-3610`.
- `POST /api/wardrobe/analyse` (single piece, no box): `gemini-2.5-flash`, `maxOutputTokens: 900, temperature: 0, thinkingConfig: { thinkingBudget: 0 }` — `server.js:3521-3540`.
- Shared field rules `ANALYSE_FIELD_RULES` and schema `ANALYSE_SCHEMA` — `server.js:≈3374-3440`; legacy has no prompt version identifiers (no `prompt_version` in `analysedPiece`, `server.js:≈3446-3490`).
- Legacy history entry for the multi-piece read (2026-10-13) lists the helpers and harness (`multipiece_harness`, port 4331) — `docs/legacy-app-history.md:209-213`.

### Inferences
- "A new prompt version as usual" for a new per-piece field means: `wardrobe-analyse/v6.ts` (+ test) extending v5, `wardrobe-pieces/v4.ts` (+ test) re-slicing v6's field rules, two export lines in `packages/ai/package.json`, and updates to any handler test or fake (`packages/jobs/src/ai.ts:16-17` imports both prompt modules) that pins the version. Inferred from the pattern above; no doc spells the steps out.

## 2. Where is the rectangle crop made, with what padding, and where is it stored? Is the original kept?

### Takeaway
Legacy crops on the client (canvas) and uploads the crop to Cloudinary folder `robes`; the platform crops on the server with `sharp.extract` inside the rendition pipeline, storing the crop as its own asset in S3. Both use the same rule: 8% padding on every side and never less than 28% of the frame on a side. Neither removes any background — the crop is a plain rectangle of the original photo.

### Cited Findings

**Platform**
- For each piece the job creates a crop asset row and copies the source photo's master to the crop asset's upload key; the rendition function then cuts it: `const cropAssetId = await deps.reads.createCrop(ctx.userId, assetId, piece.box); const key = mediaKeys.original(ctx.userId, cropAssetId); await deps.storage.copyObject(masterKey, key);` with the comment "Each crop is its own upload of the master; RenditionFn cuts and renders it." — `platform/packages/jobs/src/handlers/wardrobe-pieces.ts:100-109`.
- `createCrop` inserts into `app.assets` with `kind: 'wardrobe'`, `provider: 's3'`, `sourceAssetId`, `crop: JSON.stringify(crop)` — `platform/packages/db/src/repos/photo-reads.ts:40-55`. Columns `assets.source_asset_id` and `assets.crop jsonb` ("fractions of the source's master") were added by `platform/db/migrations/20261015300000_photo_pieces.sql:10-16`; the same migration adds `wardrobe_items.source_asset_id` and `source_index` (0–7) with a unique index per (user, source asset, index) (`:18-25`).
- The cut itself: `processUpload` reads `asset.crop` and does `master = crop ? await renderMasterImage(await cropImage(original, crop), 'jpeg') : await renderMasterImage(original, format)` — `platform/packages/media/src/process.ts:85-90`. `cropImage` = `sharp(upright.data).extract(cropPixels(box, width, height)).jpeg({ quality: 90 })` — `platform/packages/media/src/render.ts:115-127`.
- Padding rule: `cropRegion(box, pad = 0.08)` — "The piece's own crop as fractions: 8% padding, never under 28% of the frame on a side", clamped to the frame — `platform/packages/core/src/photo-pieces/index.ts:33-52`; `cropPixels` converts to sharp's extract region (`:54-69`). The padding is a fraction of the whole image, not of the box.
- What is stored per asset: `uploads/{userId}/{assetId}/original`, `media/{userId}/{assetId}/master.jpg` (max 2048 px edge, EXIF stripped, `flatten({ background: '#ffffff' })`, JPEG q85), renditions `{320,640,1080,1600}.{avif,webp}` — `platform/packages/media/src/keys.ts:5-24`, `platform/packages/media/src/render.ts:9-14, 45-60`. The master is always JPEG flattened onto white, so today's pipeline cannot carry transparency in `master.jpg`.
- The filed piece points at the crop: `imageAssetId: piece.cropAssetId` — `platform/app/src/server/photo-reads.ts:111`; DB column `wardrobe_items.image_asset_id` (`platform/db/migrations/20260924000500_wardrobe.sql:37`). An owned piece with no photo "takes the crop" (`adoptPhoto`), and crops nobody took are discarded (`discardCrops`) — `photo-reads.ts:128-145`.
- Original kept: the whole source photo remains its own asset (the crop rows reference it by `source_asset_id`, and `wardrobe_items.source_asset_id` references it). Documented lifecycle: "`uploads/` expire 30 d" and Intelligent-Tiering on `media/` after 30 d — `platform/docs/infrastructure.md:≈122`; key layout `:101-110`.

**Legacy**
- Client-side canvas crop: `_rbCropDataUrl(dataUrl, box, pad)` — `const pd = pad == null ? 0.08 : pad; let x = (b.x - pd) * W, y = (b.y - pd) * H, w = (b.w + 2 * pd) * W, h = (b.h + 2 * pd) * H; const minW = W * 0.28, minH = H * 0.28; … const scale = Math.min(1, 900 / Math.max(w, h)); … c.getContext('2d').drawImage(img, x, y, w, h, 0, 0, c.width, c.height); resolve(c.toDataURL('image/jpeg', 0.86));` — `public/js/dashboard-personalize.js:1505-1532`. So: 8% pad, 28% minimum side, longest edge ≤ 900 px, JPEG 0.86.
- The crop is hosted through `_rbHostDataUrl` → `POST /api/wardrobe/upload` — `public/js/dashboard-personalize.js:1533-1541`; filing hosts `pc.crop || mp.photo` per kept piece (`:5139-5140`).
- `/api/wardrobe/upload` uploads to Cloudinary (`server.js:4741-4753`); `cloudinaryUploadFile` signs with `folder = 'robes'` and returns `secure_url` with `/image/upload/` rewritten to `/image/upload/f_auto,q_auto/` — `server.js:≈299-332`. The URL lands in `wardrobe_items.image_url` (history: "one PATCH on `image_url`" — `docs/legacy-app-history.md:210`).
- The server never crops in legacy: grep of `server.js` for `c_crop`, `e_trim`, `sharp`, `extract` finds nothing image-related; the `/api/wardrobe/pieces` comment says the box exists "so the client can pin a numbered tag on the photo and cut the piece's own crop" (`server.js:≈3565-3567`).

### Inferences
- On both apps a piece added from a single-piece photo (no multi read, or one piece found whose box is the whole frame after `normaliseBox`) keeps the whole photograph as its image; only multi-piece reads produce a tighter rectangle. Inferred from `normaliseBox` (`photo-pieces/index.ts:21-31`) and the legacy fallback `pc.crop || mp.photo`.
- With an 8%-of-frame pad and a 28% minimum side, a crop of a small item (shoes, a bag, jewellery) on a worn-outfit photo necessarily includes neighbouring garments, body and background. Inferred from the arithmetic; not measured.

### Gaps
- Whether the platform's whole source photo asset is ever discarded after filing (beyond the documented 30-day expiry of `uploads/`) was not traced; `stale-uploads.ts` was not read.
- Legacy: whether the whole original photo is hosted for a wardrobe add (as opposed to a look-from-photo, where it becomes the look's record) was not confirmed; `_waMp.hostedPhoto` exists (`dashboard-personalize.js:4896`) but its writers were not read.
- The 30-day `uploads/` lifecycle is from docs; the CDK bucket rule was not checked.

## 4. How are piece images used later, and which image goes to the image generator?

### Takeaway
The image generator (`gemini-3.1-flash-image`) receives each owned piece's stored photograph as a numbered inline reference image — on the platform the piece asset's `master.jpg` (the rectangle crop, or the whole photo), on legacy the Cloudinary `image_url`. Nothing is masked or cut out first; until PR #242 the only instruction was "reproduce this exact garment faithfully", and PR #242 changed that line to "take ONLY this garment from that photograph, whoever wears it and whatever else it shows".

### Cited Findings
- Platform saved-look render: for each piece, `photo = await deps.storage.getObject(mediaKeys.master(ctx.userId, p.imageAssetId)); if (photo) references.push({ mimeType: 'image/jpeg', data: photo });` when the asset is `ready` and `references.length <= MAX_PIECE_REFERENCES`; then `deps.ai.generateImage({ feature, capability: 'image.hero', prompt, references, aspectRatio: '4:5' })` — `platform/packages/jobs/src/handlers/look-render.ts:252-289`. `MAX_PIECE_REFERENCES = 9` (`platform/packages/ai/src/prompts/avatar/v1.ts:118`).
- Platform frame (suggested/draft looks): model/twin image first, optional close-up, the key piece's photo, then each owned piece's `master.jpg` up to `MAX_REFERENCES` (9, `style-piece/v3.ts:19`) — `platform/packages/jobs/src/handlers/look-frame.ts:185-212, 240`; header comment "the key piece's photo, then each of her pieces' photographs as numbered references; proposals are named" (`look-frame.ts:24-25`).
- `image.hero` = `gemini-3.1-flash-image`, $0.50/1M input tokens, 67,000 micro-dollars ($0.067) per 1K image, 101,000 per 2K — `platform/packages/ai/src/models.ts:58-65`. Image call config: `responseModalities: ['IMAGE']`, `imageConfig: { aspectRatio, imageSize: req.imageSize ?? '1K' }` — `platform/packages/ai/src/gemini.ts:114-131`.
- The garment line in the image prompt before PR #242: "- IMAGE N: the {name} ({detail}) — reproduce this exact garment faithfully: its true colour, cut, fabric and details." — `platform/packages/ai/src/prompts/style-piece/v3.ts:341`, `avatar/v1.ts:102`; key piece: "IMAGE N shows the key piece only — reproduce the piece faithfully, but compose an entirely new scene; never copy that photo's framing, background or crop." — `style-piece/v3.ts:332`.
- After PR #242 (`platform/packages/ai/src/prompts/garments.ts`): the line becomes "— take ONLY this garment from that photograph, whoever wears it and whatever else it shows, and reproduce it faithfully: its true colour, cut, silhouette, fabric and details, never a generic version of it.", plus "Its shape: …" from `silhouette_fit` and a "LAYERS, from the skin out: …" line. The file's comment: "her pieces are often photographed on her, with the rest of an outfit".
- `cutout_asset_id` is never read by the render or frame handlers (grep: no `cutout` in `platform/packages/jobs`).
- Legacy `/api/style` image loop: `const ref = p.wardrobe_match && imgN < 10 ? await pieceRef(p.wardrobe_match.image_url) : null;` → pushed as `inlineData`, with the same "reproduce this exact garment faithfully" line — `server.js:≈879-917`; comment: "words about a black coat draw any black coat. The pieces list is now the authoritative content of the frame, each photographed piece a numbered IMAGE the model must reproduce" (`server.js:≈872-877`). Legacy `/api/avatar/render`: "up to 9 photographed pieces ride as images (1 avatar + 9 garments stays well inside the 14-reference budget …)", fetched with `fetchCloudinaryB64(p.image_url)` — `server.js:≈4477-4494`.
- Wardrobe cards / lists on the platform show the same asset through signed renditions (`media/{userId}/{assetId}/{w}.avif|webp`) — `platform/docs/infrastructure.md:≈117`, `platform/packages/media/src/keys.ts:21-24`; `platform/CLAUDE.md` names the components (`CardRow`/`CardTile` in `app/src/components/wardrobe/piece-card.tsx`, `mobile/src/features/wardrobe/PieceCard.tsx`; `RackCard` rows on a look).
- PR #242's own diagnosis of the leak, marked inferred there: "**Garments leaking in** (inferred): her piece photos are mostly her wearing them with a whole outfit, and the image prompt said only 'reproduce this exact garment faithfully'." — PR #242 body, "Causes".

### Inferences
- The generator sees everything inside each crop rectangle (other garments, body, room). PR #242 addresses this with prompt wording only; no pixel-level isolation exists. A true cutout would be swapped in at exactly two lines on the platform (`look-render.ts:260` and `look-frame.ts:≈200`, both `mediaKeys.master(userId, p.imageAssetId)`), plus the key-piece photo (`look-render.ts:471-473`).
- Because `master.jpg` is flattened onto white JPEG, a transparent cutout cannot reuse the master path; a cutout sent to Gemini would need its own key/asset (the existing `mediaKeys.cutout` is PNG/WebP).

### Gaps

## 5. Cost logging: legacy `generation_log` and the platform ledger

### Takeaway
Legacy logs every Gemini call to Supabase `generation_log` with total tokens and latency but no cost column; `gen_id` lives inside `detail`. The platform's equivalent is `app.generation_calls` written by `ledger.record(...)`, which stores tokens, image count and `cost_micros`, feeds a per-model-family daily budget breaker, and adds the cost to the job row. The platform ledger's record shape is provider-agnostic, so a non-Gemini per-piece cutout cost fits it as a new `feature`/`model`/`family`.

### Cited Findings
- Legacy table: `public.generation_log (id, user_id, endpoint, model, tokens_used int, latency_ms int, status, prompt text, response jsonb, detail jsonb default '{}', environment, created_at)` — `supabase/admin_capture_migration.sql:65-78`; admin-read-only RLS (`:85-88`).
- Legacy wrapper: one monkey-patch of `ai.models.generateContent` writes a row per call via `glog(...)` with `tokens_used: r.usageMetadata.totalTokenCount`, `latency_ms`, `status` (`'partial'` when an image model returns no image), full `prompt`, `response`, and `detail: { input_images, gen_id?, user_prompt? }` — `server.js:129-172`. `genId` is client-minted and read from the request body (`server.js:≈84-89`); request context is carried by `AsyncLocalStorage` (`server.js:79-92`). It is a no-op without `SUPABASE_SERVICE_ROLE_KEY` (`server.js:95, 173-175`). No cost is computed anywhere in the wrapper.
- The legacy database is frozen (2026-11-03): no new `supabase/*.sql`, new DB work is a platform migration — root `CLAUDE.md` "Keep beta up".
- Platform table: `app.generation_calls (id, job_id, user_id, feature text, model text, tokens_in int, tokens_out int, images int default 0, latency_ms int, status in ('ok','partial','timeout','error','cancelled'), cost_micros bigint default 0, prompt text, response jsonb, detail jsonb default '{}', created_at)` partitioned by `created_at`, comment "prompts/responses are purged after 30 days (SEC-82)" — `platform/db/migrations/20260924000700_generation.sql:52-73`. Also `app.platform_budget (day, model_family, cost_micros, limit_micros)` (`:84-90`) and `generation_jobs.cost_micros` (`:19`).
- Platform writer: `ledgerRepo.record(call: CallRecord)` inserts the call, upserts `platform_budget` by `call.family`, and adds `costMicros` to the job — `platform/packages/db/src/repos/ledger.ts:5-75`. `CallRecord` fields: `jobId, userId, feature, model, family, tokensIn, tokensOut, images, latencyMs, status, costMicros, prompt?, response?, detail?`; "`detail` outlives the 30-day purge" and must never hold her words (`ledger.ts:17-22`).
- Cost computation: `textCostMicros = round(tokensIn * inputPerMTok + tokensOut * outputPerMTok)`; `imageCostMicros = round(tokensIn * inputPerMTok + images * perImage)` — `platform/packages/ai/src/models.ts:75-88`. For text, `tokensOut = candidatesTokenCount + thoughtsTokenCount` (`gemini.ts:86-96`).
- Call-site pattern (the wrapper is per handler, not global): `await deps.ledger.record({ ...result.usage, jobId: ctx.jobId, userId: ctx.userId, feature: FEATURE, status: 'ok', response: result.data })`, and on `AiError` with usage, a row with `status: 'timeout' | 'error'` — `platform/packages/jobs/src/handlers/wardrobe-pieces.ts:75-98`, `wardrobe-analyse.ts:74-99`.
- Budget breaker: `DAILY_BUDGET_MICROS = { 'gemini-flash-lite': 20_000_000, 'gemini-flash': 50_000_000, 'gemini-image': 150_000_000, 'gemini-image-lite': 100_000_000 }`, any other family gets `DEFAULT_DAILY_BUDGET_MICROS = 10_000_000` ($10/day) — `platform/packages/core/src/budget/index.ts:1-14`. The photo-read route refuses when `gemini-flash` is exhausted and charges quota `{ metric: 'analyse.photo', cost: 1 }` — `platform/app/src/server/photo-reads.ts:43, 48-52`.
- There is no `gen_id` on the platform; correlation is `job_id` (`generation_calls.job_id`, index `generation_calls_job_idx`, `20260924000700_generation.sql:72`).
- PostHog also receives AI metrics on the platform (PR #242: "`lookChecks` adds `tops`, so `$ai_metric` shows whether two-top looks stop"; workers need `ROBES_POSTHOG_KEY`).

### Inferences
- A per-piece cutout from a non-Gemini provider could be recorded by calling `ledger.record` with e.g. `feature: 'wardrobe.cutout'`, `model: '<provider model>'`, a new `family`, `images: 1`, `tokensIn/out: 0` and a computed `costMicros`; a new family would need an entry in `DAILY_BUDGET_MICROS` or it falls under the $10/day default. The `AiProvider` interface is typed `name: 'gemini' | 'fake'` with only `generateJson`/`generateImage` (`platform/packages/ai/src/provider.ts:46-50`), so a cutout provider would be a new adapter or method — design choice, not something the repo decides.
- In legacy there is nowhere to record a non-Gemini cost without new code (the wrapper only wraps Gemini) and no cost column; given the DB freeze, cost logging for a cutout belongs on the platform.
